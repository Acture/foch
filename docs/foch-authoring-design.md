# Foch Mod 作者工具链：产品设计

状态：产品设计持续维护；事件测试框架已实现，尚未发布。更新于 2026-10-07。当前可用接口见 [事件测试使用说明](./foch-runtime-tests.md)，当前架构见 [架构](architecture.md)。

本文是 Foch 面向 EU4 mod 作者的产品设计入口，定义使用流程、接口方向和交付要求。私有笔记的 `notes/research/` 保留另一条探索路线及其候选设计；本文独立维护产品决策，只引用研究中的可验证证据，不直接继承实验脚本、语法或执行方式。

## 产品目标与已确定要求

作者在维护 mod 的原生代码时，可以就地声明测试、发现可用 API、运行静态检查，并对具体事件和机制做可重复的运行验证。工具链保持轻量，通过同一个 `foch` 命令使用。

当前讨论已明确的要求：

- 提供 `foch lint`、`foch compile`、`foch merge`、`foch test` 的统一入口。
- 支持同文件测试，注解体验向 `#test(time=..., tag=...)` 收敛。
- 带测试的原生 mod 文件直接交给 EU4 仍然合法；正常游玩和发布不以先运行 Foch 为前提。
- 用 `time = 1444.11.11`、`tag = SWE` 直接表达精确到天的开局日期和国家，作者无需先理解或定义具名 fixture。
- 特殊前置条件先由作者编写原生效果或准备事件，之后再根据实际复用需求提供通用脚本。
- 测试覆盖具体事件与机制，并逐步提供有预算的参数化、fuzz 和失败重放。
- API 必须可发现：编辑器补全、悬停、诊断和参考说明属于产品体验。
- 运行测试最终面向平台托管 CI，不要求用户准备自托管 runner；本地原型跑通不能代替托管环境验收。

这些是产品要求；下面推荐的参数细节、默认行为和实现边界仍有待定项，不能据此宣称功能已发布。

## 命令职责

| 命令 | 作者目的 | 职责与边界 |
| --- | --- | --- |
| `foch lint` | 在编辑和提交时发现问题 | 静态检查原生源码及测试声明；与编辑器共享诊断，不启动游戏 |
| `foch compile` | 生成需要的构建产物 | 只用于需要编译成原生脚本的扩展；测试层由 `foch test` 生成（`--no-run` 只生成不运行），不经过 compile。完整输入、输出及默认模式仍待定义 |
| `foch merge` | 合并有序 mod 输入 | 保留既有分析、审阅、确认及独立输出契约 |
| `foch test` | 运行选中的测试并定位失败 | 自动收集、校验、执行所需测试编译，再运行并报告；不要求作者手动串联多个命令 |

正常 EU4 `.txt` 文件与测试注解可以直接发布，compile 不承担“先修复源码才能让 EU4 加载”的前置职责。`test` 不暗中替作者解决 merge 冲突；测试合并结果时，明确指定已生成的被测产物或有序输入。

目前已有 `check` 面向 playset 分析。新增 lint 应复用相关能力，同时明确面向作者源码的诊断范围；不能仅改名后丢掉现有 check 语义。静态检查能发现类型、scope、引用等已建模的问题，但不证明事件自然触发或机制正确。

## 同文件注解体验

以下是本轮已实现的事件测试接口：

```text
namespace = reforms

#test(time=1444.11.11, tag=SWE, expect={ has_country_flag = reform_done })
country_event = {
	id = reforms.1
	title = none
	desc = none
	picture = none
	hidden = yes
	is_triggered_only = yes
	immediate = { set_country_flag = reform_done }
	option = { name = OK }
}
```

推荐让注解附着于紧随其后的原生定义。Foch 读取注解和事件 ID，生成“准备开局 → 调用事件 → 检查结果”的测试；作者无需重复指定被测事件 ID。对 EU4 来说，注解是一行普通注释，下面的定义仍然是原生事件。

这个设计借鉴属性宏的使用体验。产品新增的内容必须完整处于注释内；多行参数每行都保留 `#`。如果下方内容是 EU4 不认识的自定义测试块，仅注释第一行仍然不满足兼容要求。编辑器应负责插入模板、延续注释前缀，并将诊断定位回原文件。

最简入口是用户提出的形式：

```text
#test(time=1444.11.11, tag=SWE)
```

用户已确定默认行为：没有 `expect` 时是明确标记的 `smoke`，只验证调用完成，不能显示成“事件效果正确”。验证状态必须提供 `expect`。

简单单事件测试是首个体验目标。多个准备事件、多次时间推进和多个检查点如何表达，属于下一步接口设计；research 中的完整注释测试块是可供比较的方案，不自动作为产品的第二套语法。

## 时间、国家与准备步骤

`time` 是加载开局状态的完整日期，`tag` 是测试开始时的国家 scope。日期按日期值处理，不作为浮点数；不隐式把一年转换成某个开局日。报告和重放材料保留实际开局日期与国家。

`advance_days` 表示从当前检查点推进真实游戏时间，再继续测试，不用修改日历值代替游戏更新。它与事件调用、即时断言的执行顺序和检查阶段需要成为稳定契约；月结算、延迟事件等同日操作不能依赖未定义顺序。

作者可以用原生 effects 或自己编写的准备事件建立战争、改革、经济等特殊状态。框架负责开局和用例隔离，作者负责声明需要的状态变化及预期。通用准备脚本库后续提供，不是首版前置依赖。

纯测试辅助事件不能因加入测试就进入正常生产加载；其存放和引用方式需随复杂场景接口一起定义。简单准备可通过测试描述生成到独立测试产物。框架不能把用户既有存档或正在游玩的实例当作默认测试起点。

## 测试能力与 API 发现

产品需要支持四类基础操作，下面名称沿用当前讨论，具体参数组织随语法统一：

| 能力 | 当前接口方向 | 必须说明的语义 |
| --- | --- | --- |
| 准备状态、执行机制 | 原生 effects | 当前 scope、前置条件与异步后续行为 |
| 主动调用事件 | 注解的目标事件；显式调用时使用 fire_event | 目标、调用上下文及支持的事件类型 |
| 推进时间 | advance_days | 相对日期、检查阶段、最大推进量和超时 |
| 验证状态 | expect 内的原生 triggers | 断言结果、观察阶段及可提供的失败信息 |

事件效果、触发条件、选项效果和自然触发分别定义能力，不能以主动调用成功代替其他三项。首个实现可以只支持经验证的事件调用路径，但必须在诊断和帮助中报告范围，不能对不支持的行为返回通过。

作者不应记忆内部实现或通读研究报告才能写测试：

- 输入 `#test(` 时补全参数，说明日期格式、tag、目标绑定与支持范围。
- 在 expect 内补全当前 scope 可用的原生 triggers；引用项目对象时提供补全和跳转。
- 悬停显示参数、例子、检查阶段和所需能力；缺失能力在运行前得到明确诊断。
- 编辑器提供运行单个测试、定位失败和查看重放信息的入口。
- 提供离线 CLI API 查询和版本化文档；首版已提供 `foch test --api [参数名]`。

测试接口使用同一份结构化定义支撑静态校验、补全、悬停和文档。原生语法复用现有 CWT/schema 与项目索引；schema 中存在某个字段不等于运行时已经支持它。

## MTTH 与自然触发测试（待实现，2026-10-02）

用户要求将 MTTH 测试纳入产品设计，本轮先记录，不开始实现。现有框架主动调用目标事件，只覆盖调用及效果；已有真实游戏结果不包含 MTTH 或自然触发概率验证。

建议分三层提供能力：

| 层次 | 验证内容 | 使用方向 |
| --- | --- | --- |
| 触发资格 | 在作者准备的状态下，原事件的 trigger 是否成立 | 低成本条件测试 |
| MTTH 配置与修正 | 哪些 modifier 生效，计算后的 MTTH 是否符合作者预期 | 日常回归；Foch 配置计算必须与引擎内部读值明确区分 |
| 自然触发概率 | 保留原始 MTTH，在独立初始状态下多次运行，记录是否发生及首次触发日期 | 单独按样本数、模拟天数和墙钟预算运行 |

MTTH 不是固定触发期限。有效 MTTH 的计算规则、时间单位、引擎检查频率及概率换算需要按 EU4 版本验证，不能套用其他游戏的实现。若先由 Foch 计算配置结果，报告必须注明计算来源；声称读取引擎内部值前，需要单独验证读取接口。

下面仅保留讨论过的接口草案，参数名、默认值和统计规则均未定稿，当前 CLI 不接受这些新增参数：

```text
#test(time=1444.11.11, tag=SWE, mode=natural,
#     observe_days=365, samples=200,
#     expect_chance={ min=0.4 max=0.6 })
```

示例表达“200 个样本中，一年内至少触发一次的概率应符合作者声明的范围”。40%–60% 是示例契约，不是某个 MTTH 数值的已验证换算；200 次也不保证统计证据充分。所有测试描述继续保留在注释内，原 mod 不需要预处理。

自然触发运行与判定要求：

- 不主动调用目标事件，保留原始触发条件和 MTTH。自然事件的收集不能沿用当前必须 `is_triggered_only=yes` 的目标限制。
- 优先建立可靠的发生观测和首次触发时间记录。首版可在语义明确时使用事件已有的专属 flag；通用事件观测接口后续设计，不能把其他效果设置的 flag 误认为目标发生。
- 每个样本从独立初始状态运行，记录不同种子、游戏版本、DLC、有序输入、准备步骤及观察期间相关状态变化。相同种子不自动保证完整重放，同一局不同国家也不能直接视为独立样本。
- 到模拟观察期限未发生是有效样本，必须保留；加载失败、崩溃和墙钟超时属于运行错误，不能记作未发生或从分母中静默删除。
- 预先确定统计方法、容许范围、置信水平和预算，报告通过、失败或证据不足。证据不足不自动算通过；未经统计设计，不以反复追加样本直到通过作为停止规则。
- 日常 CI 优先覆盖条件和 MTTH 修正；概率分布测试独立按预算运行。临时缩短 MTTH 的测试只证明对应测试条件下的触发链路，不证明原始概率。

建议的首个实现增量是“自然触发观测＋首次触发时间记录”，有可靠记录后再增加统计判定。自然模式省略概率断言时如何报告，仍待定义；不能直接继承主动调用模式的 smoke 成功语义。

## 运行接口与扩展方向

先形成稳定的运行时测试接口，再考虑更广泛的作者扩展能力。接口围绕用例身份、开局参数、支持能力、执行步骤、观察结果和结束状态组织，不把研究脚本文件名或日志字符串直接暴露成作者 API。

具体实现可以依据已经验证的游戏入口生成和执行脚本；以后需要 DLL 才能提供的读取、控制能力，也通过明确的能力声明接入。切换执行方式不应要求作者重写语义相同的测试，也不能把不同实现的时序差异隐藏成完全等价。

已拆分为内部库：注解机制 `foch-annotation`、测试含义与判定 `foch-test`、内置运行器 `foch-runner`，语言服务 `foch-lsp`，均由 `foch` 可执行文件使用；桌面应用直接链接库，不经 CLI sidecar。`foch test` 用内置运行器启动真实游戏，默认关闭 AI，按 `expect` 顶层子句逐条检查，真实用户目录靠备份+校验保护。当前边界见 [架构](architecture.md)，用法与实测边界见 [使用说明](foch-runtime-tests.md)。

## 测试工作流与结果

作者应能从项目根目录运行全部测试，按文件、用例或名称筛选，只收集用例，以及重放失败。用例具有稳定身份，错误指向原始注解或断言位置，不能只给生成事件的行号。

结果区分断言失败、环境或加载错误、崩溃、超时和显式跳过。没有游戏、目标不支持、缺少预期检查或未完成运行都不能算通过。终端、机器报告和退出码表达同一结果。

失败信息先展示实际获得的证据。只有布尔 trigger 结果时，不伪造内部数值或完整因果解释。复现材料记录游戏版本、DLC、有序输入、开局和准备步骤，以及生成的实际 fuzz 输入；单独保存随机种子不足以保证整局确定性。

参数化和 fuzz 复用同一测试契约，有明确的用例数、模拟天数和墙钟预算。先做限定参数域的生成，再扩展操作序列。失败在独立起点重放后才尝试缩减；保持同一失败原因，不承诺找到数学意义上的最小例子。

## 轻量与托管 CI

lint、测试收集和测试编译不启动游戏。运行测试按声明选择所需能力，固定资源可缓存；任何批量运行优化都必须先证明用例之间没有状态污染。

托管 CI 的交付包含版本固定的运行材料提供方式、资源预算、冷启动验证和失败材料导出。游戏文件取得方式与运行方式分别处理；本地实验无需 Steam 登录的结果不能自动证明所有发布环境可用，也不能替代实际托管 runner 验收。

原游戏、DLC 和源 mod 是只读输入。测试运行使用独立产物、配置和存档，只控制自身启动的进程。这些运行隔离要求与“同一份源文件可直接被 EU4 加载”分别验收。

## 交付验收与当前状态

首个产品版本至少需要证明：

1. 带产品注解的原生文件未经 Foch 预处理即可被 EU4 加载，原有行为检查仍有效。
2. Foch 能发现、绑定和执行注解测试；正确预期通过，错误预期失败，诊断准确回到原文件。
3. 不支持的目标、无效开局、缺失结果、超时和崩溃有明确的非通过结果。
4. API 补全、静态诊断和实际执行的能力说明一致。
5. 用例隔离、失败重放及限定预算的参数测试可验证，并有平台托管 CI 的真实运行结果。

本地工作树已实现注解收集/校验、`foch test --no-run`、`foch test --collect-only`、API 查询及显式 `--runner` 执行，LSP 已接入参数补全、悬停和注解诊断。运行判定检查实际游戏日期、完整标记及错误日志。当前支持隐藏且仅主动触发的 country_event，准备 effects 和单个即时/延迟断言。详见 [当前接口和运行端边界](./foch-runtime-tests.md)。

尚未实现独立 lint 命令、注解内原生 trigger/effect 补全、运行按钮、多步骤/fuzz/自动重放、通用运行环境和托管 CI 验收。现有 `foch.toml` 未新增测试配置字段。首个框架闭环不代表以上完整产品验收已经完成。

研究已验证 EU4 1.37.5 的特定运行通路，以及完整注释测试块直接加载的兼容性，原始材料见 [研究夹具](../src/apps/foch-cli/tests/probes/eu4-runtime/headless-probe/) 和 [注释兼容性结果](../src/apps/foch-cli/tests/probes/eu4-runtime/headless-probe/inline-comments-result.json)。这些保留为局部可行性证据；产品编译器有独立实现和验证记录。

本产品能力使用自己的验收，不替换固定 14-case 的 `cargo acceptance` 合并质量门槛。

## 继续设计的事项

- compile 的完整职责和默认构建目标；测试不使用 compile。
- 在已实现参数、目标绑定和 smoke 默认行为上扩展能力版本约定。
- 多步骤测试、作者准备事件和测试辅助内容的组织方式；保持单一、连贯的作者体验。
- 支持的首批事件/机制类型、断言观察阶段及运行能力版本约定。
- MTTH 的自然触发观测、修正计算来源和有预算的统计判定；见上面的待实现记录。
- 托管 CI 的运行材料、资源预算和实际验收环境。

后续产品决策更新本文；research 可独立比较或验证其他路线，不因研究文档变化而隐式改变这里的产品契约。
